# Testing

Firmware parts are written; PL simulation sections are for the PL owner to add (see
[`fpga/pl/README.md`](../fpga/pl/README.md#simulation)).

## Host tests (firmware)

```bash
cd firmware/stm32wl/tests
./run_tests.sh
```

Needs only `gcc`. `subghz_phy_app.c` is compiled with stub HAL, radio and timers (`tests/stubs/`) and driven with
scripted packets. The stub `net_key.h` holds the test key `00 01 ... 0F`.

| Group | Covers |
|---|---|
| `crypto` | AES-128 (FIPS-197) and CCM vectors |
| `mesh_relayer`, `mesh_far_node`, `mesh_gateway` | Relay both directions, suppression, flag stability, gateway routing |
| `join_node`, `join_gateway` | JOIN, kick, leave |
| `secure_node`, `secure_node_only`, `secure_gateway`, `secure_join`, `secure_gw_only` | Envelope, counter storage, replay window, rejection of forged / corrupt packets, gateway queue |
| `relay_sel_relayer`, `relay_sel_far_node` | Relayer choice (score, hysteresis, fallback), `0x52` handling |

Last run (V1.17.3): all 13 groups pass, plus the `golden` group (see below) when `docs/protocol/golden/golden_frames.json` and `python3` are available.

## Golden frames

Byte-exact frames shared by firmware tests and PL testbenches live in
[`protocol/golden/golden_frames.json`](protocol/golden/golden_frames.json). Test key `00 01 ... 0F`; every frame was
generated by the firmware in the PC harness and decrypted independently with Python `cryptography` AESCCM (tag
length 4).

| Check | Command |
|---|---|
| Firmware CCM against the file (`golden` group) | `firmware/stm32wl/tests/run_tests.sh` |
| Independent check | `python3 -I docs/protocol/golden/verify_golden.py` |

PL testbench generators (`fpga/pl/tb/gen/fw_golden_frames.py`) currently keep a copy of five of the frames.

## Results

### Indoor walk (V1.15, plain mode)

Gateway and one node fixed, the other node carried behind thick walls.

- Gateway signal at the worst point: -95 dBm, SNR +9 dB. 35 of 37 tables arrived and every position sent reached the
  admin. With SF7 sensitivity of about -124 dBm that is roughly 30 dB of margin.
- The other node was about 20 dB weaker at the same point (-107...-109 dBm, SNR -8 dB, at the SF7 limit) and lost
  part of its packets there. Antenna and placement to be investigated.
- The two lost tables were collisions, not range: one from two transmitters at the same time, one from a node
  missing the table while transmitting (half-duplex).

### Security migration (V1.16)

Secure packets verified in the Zybo counters, replay count 0. Nodes decrypted the Zybo's secure table and commands;
mesh relay worked with nested envelopes.

### Relay selection field tests (V1.17.x)

- Reducing only the gateway's TX power weakens the downlink but not the uplink (gateway RX stays about -124 dBm
  sensitive). Nodes then request a relay while their direct uplink still arrives, which shows as "+D" in the admin
  GUI. Realistic tests need both directions reduced, or real distance.
- Score = min(link quality, GW quality) by design: a node chooses a strong-link neighbour over a weak-link one with a
  better GW quality. The box node kept choosing BRAVO-1 over the centre node at -115 dBm / SNR -9.
- V1.17.1: the Zybo kept a silent node's old table record, so the node thought it was reachable; fixed with
  `OWN_SEQ_FRESH`.
- V1.17.2 / V1.17.3: exit from relay mode reworked (direct-table streak, `E3` copies do not reset it, SNR >= 0 dB).
